# Agent instructions: The Trestleboard

If something I ask conflicts with this file, do what I asked and mention the conflict. If it would lose content or saved data, or cost money, check with me first.

## Project
- What this is: the Trestleboard, an app of 24 practices drawn mainly from Freemasonry, Kabbalah, Hermeticism, alchemy, and Christian mysticism, used as psychological tools, plus 18 small practices for steady moments, the Watch (a breathing companion meant to run in the background all day like a video: you pick one or more of four breathing patterns taken from the practices, or a mix, press Start, and it breathes with you set after set, with short rests between and no set end, over a blend of generated sounds, showing where each pattern comes from while it runs; it has a large Pause button, and its setup starts from the defaults each time the app is opened; it keeps running while you move to other pages, with a slim bar above the tabs, and its breathing waits while a practice, a routine, or the timer is on screen), *A Field Guide to the Western Mysteries*, and a personal log. Mainly for my own use, but kept shareable.
- Platform: an offline-capable web app I use from my iPhone home screen and in a browser on my computers, hosted on GitHub Pages. I edit it on a Windows PC.
- Saved data is per device: each phone or browser keeps its own, and nothing syncs between them (backup and restore copies it across).
- Location: this folder is the whole site and the git repository, and it is public on the web. Never put secrets or anything private in it; save notes, reports, and drafts in the parent Trestleboard folder instead. If you can't write there, put them in your reply, never in this folder.
- Layout:
  - `index.html` is the whole app, in three parts: styles, then a JSON block (`id="book"`) holding all the book text, then the script. Edit it directly. There is no build step, and the old build scripts are gone; don't look for them or recreate them.
  - The 24 practices' wording (method, why, and the rest) is in the book block under `entries`, by number. In the script, `E` holds each practice's situation label, tool, and a copy of its name; the tools' on-screen step labels and closing lines are there too, and are spoken. The breathing patterns are in `P` (labels, timings, and spoken `say:` lines), shared by the practices and the Watch. The small practices are `EVERY` (by text id, such as `attention`), with all their text in the script. Three blocks of text are unused: `WATCH_SAYS` (how the old Watch worded each small practice), `HOURS` (the monastic hours), and `SECTIONS` (old section names). They're kept on purpose until the Watch's reading feature is settled, since they may become reading material. The day correspondences are `DAYS` (with `dayAbout` explaining them). The Watch's four breathing patterns are `WB` (each points to its practice by number) and its mixes are `W_MIXES`; the running Watch is `W` (started and stopped by `watchStart` and `watchStop`, paused by `watchPause`, so it outlives page changes), its page is `watchView`, its slim bar on other pages is `wMiniDraw`, its sound layers are `wLayer` (listed in `W_LAYERS`), the bell at the start of each set is `watchBell`, and its soft music is `startMusic`.
  - `sw.js` is the service worker (the background script that keeps a copy of the app on the phone for offline use).
  - `voices/` holds the two built-in voice recordings (Heart, Michael). `manifest.webmanifest` and `icons/` set the home-screen name and icon. `README.md` is the repository's front page on GitHub, not part of the app.
- Preview locally: serve the folder over localhost (on Windows, `py -m http.server 8000`, then open http://localhost:8000). Opening index.html directly turns off the offline features and the built-in voices.
- Git: I commit and publish with GitHub Desktop myself. Don't commit, push, or publish.

## Don't break these
- Saved data: everything I save lives on each device in localStorage under `tb:` keys, read and written only through `store.get`/`store.set` (they add the prefix). The one exception is the backup and restore code, which copies every `tb:` key as-is; leave it that way. Never rename, remove, or change the format of those keys. Saved items point to practices by number and to note fields by position: don't renumber practices or insert note fields in the middle; add new ones at the end. Small practices are found by their text id; don't rename those ids.
- Offline updates: whenever you change any file the app loads (not README.md or this file), update `CACHE` in `sw.js` once per task, before your first preview if you can preview: add 1 to the number and use today's date (e.g. `trestleboard-v10-2026-10-19` → `trestleboard-v11-<today>`). Keep the `trestleboard-` start, because old copies are deleted by that name.
- `FILES` in `sw.js`: every path must exist and look like `icons/x.png` (no leading slash), apart from `./`, which stands for the front page; keep it. One bad path silently stops the phone from ever updating. Add every new file the app loads (a font, an image, a script) to `FILES`, so it's there the first time the app opens offline. Never list `voices/` there.
- Voices: the built-in voices are recordings of exact lines, and the tools that made them are gone. Changing any text the app speaks (practice names and steps, tool step labels and closing lines, breathing `say:` lines in `P`, routines, timer prompts, the line of the day) makes that line fall back to the phone's own voice; tell me which lines changed. Before changing any wording, check whether it's spoken: search the list that `trestleboardPhrases()` returns in the browser console (without a browser, read `allPhrases` in index.html, which builds that list). Don't change the voice files or `VOICE_CACHE` without asking. The small practices, the Watch, and the day correspondences aren't spoken at all; that's on purpose, not a bug. New lines can't be added to the built-in voices, so anything you make spoken uses the device's voice; tell me when that happens.
- Shared breathing patterns: `P` is used by both the practices and the Watch, and its `say:` lines are spoken. The Watch uses `P`'s timings, not its `say:` lines. For a Watch-only change, give the Watch its own copy of that pattern outside `P` (beside `WB`) instead of editing `P`. Never edit `P` without telling me which practices it affects, and that the Watch's timing changes too.
- Book text: the `id="book"` block is one JSON line about 190,000 characters long. Change it only with exact find-and-replace (never by rewriting the block with a JSON tool), keep every `<\/` as written, and reload to confirm the app still opens. One stray quote or comma blanks the whole app.
- Offline use: the app loads nothing from the internet. Keep it that way: anything new (fonts, scripts, images) goes into the project. Links out to reading sources are fine.

## Content rules
- Keep the writing as it is unless I ask. Rewording also matters because spoken lines are tied to the voice recordings.
- Don't remove or shorten any content (text, practices, glossary entries, drawings, helper text) without asking; earlier versions were merged into this one. A direct request from me to shorten, reword, or remove a named item is the permission; ask only if it's unclear which item I mean or the change would reach other items. The two-week test and the calendar were dropped on purpose; don't bring them back.
- When you do write: treat the traditions as psychological tools. Don't present supernatural claims as literal, but keep the symbolism and sense of mystery; they're part of what keeps the practice motivating.
- Tone: a hybrid. Precise and slightly technical, but human and readable, never robotic or cold. Direct, with no flattery and no filler introductions.
- No evidence ratings or scores (dots, stars, grades) on practices; they imply more credibility than intended.
- Keep my personal life (family, work) out of the content.
- Sources: only free or public-domain material.

## Interface and design
- Navigation (the bottom bar, moving between pages) should feel smooth and fluid. When working on it, short transitions like the existing ones and icons that match the tab icons are fine. Put any new animation inside the existing `@media (prefers-reduced-motion: no-preference)` block, even though older animations are switched off in a separate `reduce` block instead (leave those as they are), and make scripted motion (such as smooth scrolling) respect the existing `reduce` variable.
- Pages should be calm: nothing overwhelming or distracting. No decorative animation, menus inside menus, or crowded layouts on reading and practice pages. Don't add new sections to the tab bar, or tab strips inside a page, without asking. Showing the existing tabs as a side rail on wide screens, or a second pane beside the main content, isn't adding tabs, as long as the page still feels calm.
- Don't add taglines, helper text, or extra labels to explain a confusing screen; fix the layout instead. Leave existing helper text as it is.
- New drawings and icons should match the existing line style: outline only (`fill="none" stroke="currentColor"`), apart from small solid dots and the solid star that marks a pinned practice; rounded corners, `aria-hidden="true"`, and the same size and stroke width as their neighbours.
- Phone first, then responsive: build the narrow layout first (about 390 pixels wide, my iPhone), then let wider screens use the extra room. Base layout changes on the window's size (CSS media queries in `rem`, like the existing ones), and mouse-only touches such as hover highlights on `@media (hover: hover) and (pointer: fine)`. Never guess the device from the browser's name (user-agent sniffing): a desktop window can be phone-narrow, and iPads report themselves as Macs.
- When you work on layout, use the common width bands from Material Design's window size classes as a guide, not a to-do list: narrow (under about 600 pixels): one column, tabs at the bottom; medium (about 600 to 840): the tabs may move to a slim side rail; wide (over about 840): room for a rail and two panes side by side. Short windows (under about 480 pixels tall, like a phone turned sideways) keep the one-column phone arrangement, with no second pane. Moving the tab bar, or reshaping pages I didn't name, still needs a request that names them. The existing breakpoints (30, 36, and 48 rem, used by the Read tables and small layouts) stay as they are; don't move them to the new bands. The 600 and 840 bands (37.5 and 52.5 rem) are for new layout work.
- At every size: reading text stays about 50 to 75 characters per line (use extra width for things placed beside the text, not longer lines); tap targets stay at least 44 pixels (the existing `--tap`); controls stay clear of the notch and rounded corners (the existing `env(safe-area-inset-*)` padding); light and dark mode both work (dark mode follows the device); and nothing may make the page slide sideways.
- Tables on the Read pages already stack into cards on narrow screens; a new table there needs a `<thead>` row and the same `<div class="table"><div class="tablewrap">` wrapper the book's tables use.
- Every control needs a label VoiceOver (the iPhone screen reader) can announce.
- Every feature should feel natural on any device and window size: phone, tablet, or computer; touch or mouse. Keep the same features wherever the platform supports them; explain any unavoidable platform limitation before considering a workaround. Only layout and small touches (such as hover highlights or keyboard shortcuts) should otherwise differ. Every action must also have a visible control that can be used with a tap, a mouse, or the keyboard; no action may depend only on hover, a keyboard shortcut, or a touch gesture. This applies to what you build or change; it isn't a reason to revisit features I didn't name. The Watch in particular is meant to run in the background all day: everything timed on it (breathing, tones, bells, and anything new that changes on a schedule) runs on clock time (`Date.now()`), not counted ticks, with tones and bells set a few seconds ahead on the audio clock, because browsers slow timers in background tabs; keep it that way. Don't spend effort on iPhone-only workarounds; if I ask for one, explain what it would take and ask before building it.
